## 0. 结论先行

**能融入，且我此前「投资评估板块不做」的判定需要修正。**

修正理由：上一轮否掉的是 `agri_project_roi`——用种植数据算 ROI，实测 110 份配方
`outcome` 非空 0 条、含 yield 0 条、经济字段 0 命中，输入不存在，硬做只能编数字。

这个系统是**完全不同的东西**：

| | `agri_project_roi`（已否） | AgriScreen（本包） |
|---|---|---|
| 输入 | 种植数据（outcome/yield/价格） | **BP / 审计报告 / 银行流水 / 证书文本** |
| 输出 | ROI 数字 | **完备性 + 风险初筛**（通过 / 需深挖 / 淘汰） |
| 编造风险 | 输入 0 条，只能编 | **自带三重防线**：无来源不计分 / 缺失区间化 / 禁止估算冒充 |
| 依赖我项目数据 | 强依赖（110 配方） | **不依赖**（自成输入） |

它恰好补上本项目两个已知短板：

1. **outcome 回流缺口**（`feedback_log` 长期 0 条、110 配方 `outcome` 0 条）
   —— `cases` / `assessments` 表 + 补数增量重算，本身就是回流通路。
2. **规则知识资产** —— 本项目有环境配置规则（Env Recipe），它带来投资决策规则
   （六分类 / 五闸 / 六评分卡 / 一票否决）。两者都是「组织方式」壁垒而非「数据本身」壁垒，
   符合 v2.0 定位的核心判断。

**方法论复利**：这是「知识底座 + 输出引擎」模式的**第二个领域实例**——同一套
（声明式规则库 + 版本化 + 可溯源输出 + 案例沉淀）在第二个领域复用。不是正交噪音。

**可能的串联点**（诚实标注：未验证需求，不作承诺）：
AgriScreen 出「通过」结论后，下一环是「这个项目该用什么种植配置」→ Env Recipe。
这是把两个板块串起来的自然链路，但需等真实调用方出现再确认。

## 1. 包内容实测

**依赖分层**（关键发现：第三方依赖全部是**函数内 lazy import**）：

| 层 | 模块 | 依赖 |
|---|---|---|
| **零依赖核心**（可直接并入） | `rules.py` 27.8KB、`scorer.py`、`classifier.py`、`gap.py`、`verifier.py`、`extractor.py`、`archiver.py`、`report.py` | 仅 `re` / `json` / 标准库 |
| **零依赖可解析格式** | `parser.py` 的 TXT / MD / DOCX 路径 | `zipfile` + `re`（DOCX 手工解 zip+XML，无 python-docx） |
| **需依赖增强** | `parser.py` 的 PDF / CSV / Excel 路径 | pdfplumber / pandas / openpyxl（**indent≥4，函数内 import**） |
| **需依赖服务层** | `server.py` | FastAPI / uvicorn |
| **需依赖 LLM** | `llm.py` | httpx（`if not llm_available(): return {}` 优雅降级） |
| **标准库存储** | `db.py` | sqlite3（WAL） |

`parser.py` 的第三方 import 全部在函数体内（`pdfplumber` L32、`pandas` L47、
`openpyxl` L52，indent 4–8），**导入模块本身零依赖**，只有调用对应解析函数才需要。
这意味着零依赖并入后 PDF/Excel 会优雅降级而非崩溃——与本项目 `agent/vision.py`
「未配置安全降级」是同一套模式。

## 2. 九层管线实测（用包内真实 BP 样例，无 LLM key 降级模式）

调用序列取自 `server.py` 主管线（权威顺序）：
`parse_file → archiver.archive → extractor.extract → normalize → classifier.classify →
verifier.verify → gap.detect → detect_conflicts → scorer.evaluate`

```
L0 归档    role=bp 商业计划书 primary ok      primary=1 verify=0
L1 解析    text 1 页 458 字符
L2 提取    llm_available=False（正则单通道降级生效）
L2+L3     19 个字段非空
L5 分类    seeds ①种业　置信度 84.9%　无需人工确认
           「关键词命中 29 分（第二名 8 分），财务结构信号命中」
L4 缺口    1 项（fatal 0 / critical 0 / normal 1）
           bio_inventory_pct 生物资产占比缺 → 提示补流动资产明细
L6 核验    5 条（见下 §3.2 重复计数问题）
L7 评分    需深挖　总分 71.8　五闸 0 触发　否决 0 触发
           反事实：「距『通过』档需 3.2 分。最短路径：改善『授权费与单位经济』
                    维度（当前 32%，维度得分 70），补齐后最多可提回 4.5 分」
L0 冲突    0（单文件，无跨源差异）
```

**规则库实测规模**：`RULES_VERSION=v1.0.0`（2026-09-18 发布）· 六分类
`seeds/agmach/digag/bioinputs/supply/livestock` · 五闸 `cash_ratio 70 /
client_concentration 60 / margin_gap -5 / unit_economics 0 / runway 18 / bio_asset 50`
（含分类适配，如养殖类现金收入比放宽至 50、SaaS 客户集中放宽至 70）·
六评分卡 × 6 维度加权 · 三档阈值 `≥75 通过 / 60–75 需深挖 / <60 淘汰`。

**设计亮点**（值得本项目借鉴）：
- `scorer.py` 文档字符串首行即「**纯确定性计算，无 LLM**」——评分完全可复现。
- 缺失维度**不打分**而是降权 + 区间化（`MISSING_SCORE_SPAN=7.0`，
  `band=min(4*len(missing),12)`），而非填默认值。
- 一票否决优先于总分（否决触发即 FAIL），符合「先看红线再看分数」的尽调逻辑。
- 反事实边界算「距下一档差几分、改哪个维度最划算」——可执行的补数建议，不是空话。
- 三库分离 + `rule_versions` 表：历史报告锁定生成时规则版本，改规则不污染旧报告。
  与本项目 harness manifest 版本化思路同构。

## 3. 实测发现的 6 个问题

### 3.1 【必须补】无 LICENSE 文件

全包扫描无任何 LICENSE / NOTICE / COPYRIGHT 文件。本项目有混合许可治理
（`sources[].license` + `license_scope`，未核实一律 `unknown` 不得猜）。
**这是融入的硬阻塞**——与 PlantVillage「README 无 license」同类风险。
需确认包的来源与授权意愿后才能落地。

### 3.2 【应修】L6 核验重复计数

```
verified | 审定品种 | 金玉188      ← 重复
verified | 审定品种 | 郑单958      ← 重复
verified | 审定品种 | 金玉188
verified | 审定品种 | 郑单958
verified | 安全证书 | 农基安证字(2025)第011号
```

`verifier.py` L16-18 的 `for kw in ["审定","品种审定"]` 对同一段库各扫一遍，
两条 kw 都命中同一正文 → 每个品种报两次。`all_text` 里「审定」必然包含
「品种审定」的场景下恒重。修法：去重或改单 kw。

### 3.3 【应修】L2 正则提取 3 处抽错

| 字段 | 实测值 | 应为 | 疑似成因 |
|---|---|---|---|
| `net_margin` | `1800.0` | `10.0`（1800万/1.8亿） | 百分比与金额正则混淆 |
| `rd_pct` | `600.0` | `60.0` | 百分比放大 10 倍 |
| `pipeline_certs` | `188.0` | `18` 或 `8` | **疑似匹配到「金玉188」品种名** |

第 3 条最值得警惕：品种名里的数字被当证书数。正则通道在中文混排文本上
缺乏锚点，这类误命中会静默污染评分输入。

### 3.4 【设计局限】区间化只防「没抽到」，不防「抽错了」

`band = min(4*len(missing), 12)` 只对**字段缺失**生效。本案例 19 个字段全部
「抽到」了（虽然 3 个是错的），`missing=0` → 区间半宽 **0** → 输出
`[71.8, 71.8]` 假装精确。

它自己声明的「禁止估算值冒充实际值」只覆盖「未提取到」，不覆盖「提取错误」。
而正则单通道恰恰最容易抽错。双通道（LLM 交叉验证）能缓解但非根治。
**接本项目时应在 L2 加合理性校验**（`0<net_margin<100`、`rd_pct<100`、
证书数与文本提及的「张/项」量词对齐）。

### 3.5 【必须改】端口 8001 硬冲突

`README.md` 与 `deploy.sh` 都用 `--port 8001`。**本项目 ECS 公网服务就在 8001**
（宿主机 8001 → 容器 8000，8000 被陌生 FastAPI 占用故改用 8001）。
并入后必须改端口（建议 8010）或仅以 MCP tool 暴露、不起独立 Web 服务。

### 3.6 【需替换】LLM 默认端点为 GLM，非本项目网关

`llm.py` 默认 `https://open.bigmodel.cn/api/paas/v4` + `glm-4-flash`。
本项目已有同机 ATEX 网关（宿主机 `:8420`，OpenAI 兼容）。
并入后应复用 `agent/vision.py` 的 `AGRI_VISION_URL/KEY/MODEL` 配置模式，
而非新增一套 GLM 环境变量。

## 4. 案例库诚实度核查

`cases.db` 实测 4 表：`rule_versions` 1 行 · `cases` 15 行 · `assessments` 1 行 ·
`supplement_files` 0 行。

15 个种子里：
- **3 个真实上市公司公开财务**：隆平高科（毛利 38/净利 13/PE 24）、极飞科技
  （毛利 30/PS 6.9/出货 8万台）、托普云农（毛利 51/PS 15/ARR 占比 45/续约 85）
  —— 用作分类基准锚点，`bench_names` 字段可追溯。
- **其余为虚构合成案例**，命名诚实（「某生物育种公司A（正对照）」
  「某智能农机公司B」），且 `outcome` 明写「压力测试案例：真实结局=未通过尽调」。
  ⚠️ 注意：「真实结局」这四个字用得不严谨——虚构公司不可能有真实尽调结局，
  应改为「预设结局」。这是文案瑕疵，不是数据造假，但并入时建议改掉。

**与上一轮我担心的「编造数字」的区别**：这里编的是**测试夹具**且明确标注，
真实公司锚点有出处。性质不同。但合成案例接入生产前需标 `is_synthetic` 字段。

**verifier 的 `LOCAL_REGISTRY` 是演示假数据**：7 个审定品种 + 4 个登记证号 +
2 个安全证书编号，全是编的。代码注释已诚实标注「MVP 演示库；生产版换真实公开数据源」。
并入时应接 **EPPO**（本项目已核实可达）+ 中国农药信息网，不要保留内置镜像库冒充核验。

## 5. 三个融入方案

### 方案 A：分层移植（推荐）

零依赖核心 9 模块 → `bp_screen/`；FastAPI 层保持独立可选；补 LICENSE。

| 动作 | 说明 |
|---|---|
| 移植 | `rules/scorer/classifier/gap/verifier/extractor/archiver/report/parser` → `bp_screen/`，改相对导入为平级 |
| 存储 | **保留 sqlite3**（标准库，案例沉淀需结构化查询；无需为风格一致换 JSON） |
| MCP | 新增第 10 个 tool `agri_bp_screen`：输入文本或已抽取字段 JSON → verdict + 逐项判读 + 深挖清单 + 反事实边界 |
| 格式 | TXT/DOCX 原生支持；PDF/CSV/Excel 有依赖才启用，否则明确提示降级 |
| 端口 | Web 层改 **8010**（避开 8001 硬冲突） |
| LLM | 复用 `AGRI_VISION_URL/KEY/MODEL` 接 ATEX `:8420`，不新增 GLM 变量 |
| 许可 | 补 LICENSE + `sources[].license` 逐条标注 |
| 核验 | `LOCAL_REGISTRY` 降级为示例库，接 EPPO + 中国农药信息网 |
| 修缺陷 | §3.2 去重、§3.3 三处正则、§3.4 加 L2 合理性校验 |

**产出**：一个零依赖核心包 + 第 10 个 MCP tool + 可选 Web 前端。
**风险**：工作量最大；`rules.py` 27.8KB 需逐段审查基准值来源。

### 方案 B：原样 vendor 收录

放 `vendor/agriscreen/`，独立运行，零集成、零改动。

**产出**：最快落地，风险最低。
**代价**：两个系统并存、不产生 MCP tool、不接 EPPO 核验、8001 端口冲突仍在、
依赖不隔离进主项目。**本质是没融入**，只是换了个存放位置。

### 方案 C：只搬规则库 + 评分内核

只取 `rules.py` + `scorer.py`（≈38KB 零依赖），L0–L6 自行重写。

**产出**：保住真正资产（声明式规则库才是壁垒）。
**代价**：L0 归档 / L1 解析 / L2 双通道提取 / L4 缺口提示语要全部重做，
工作量可能超过方案 A。

## 6. 推荐与理由

**推荐方案 A**，理由：

1. **依赖是分层可控的**，不是二选一。零依赖核心可直接并入，PDF/Excel/FastAPI
   作为可选增强优雅降级——本项目 `vision.py` 已验证过这套模式可行。
2. **规则库是真正资产**，27.8KB 声明式知识（六分类关键词权重 + 五闸含分类适配阈值 +
   六评分卡 6 维度阶梯 + 一票否决条件 + 三级缺口 + 补数提示 + 字段 Schema 正则）
   重写代价远大于移植。
3. **sqlite3 是标准库**，不需要为了「项目用 JSON」的风格一致性牺牲结构化查询能力。
   案例沉淀场景 SQLite 更合适。
4. **补上 outcome 回流缺口**是本项目长期短板，A 方案的 `cases/assessments`
   表 + 补数增量重算正好是通路。

**不推荐 B**：没解决端口冲突、许可缺失、依赖隔离，只是挪了个位置。
**不推荐 C**：重写 L0–L6 的工作量与收益不成比例。

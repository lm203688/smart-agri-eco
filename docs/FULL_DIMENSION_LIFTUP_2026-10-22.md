**综合得分：6.2 / 10。项目"内核很硬、外壳偏软"——前沿性与全面性已达行业中上，使用性与互动性是最大短板，且这两项恰好是决定"能否被真实用户用起来"的关键。**

| 全面性 | **7.0** | 23 工具 / 14 类 / 152 配方覆盖广，但缺采后、经济、实时天气、畜牧 |

## 2. 五维逐项评估

### 2.1 全面性 —— 7.0 / 10

**优势（实测）**
- 工具覆盖 14 类：climate(3) / crop(1) / phenology(1) / pest(1) / nutrition(1) / recipe(3) / meta(5) / soil(1) / business(1) / knowledge(2) / forecast(1) / bp_screen(1) / counterfactual(1) / verify(1)
- 链路完整：气候分区 → 作物推荐 → 物候 → 病虫害 → 营养液 → 土壤 → 配方 → 商业筛选 → 血缘/信任 → 反事实/验证
- 数据面广：152 配方、全球 11,946 气候栅格、8 大分区、7 作物权威参数

**缺口（按影响排序）**
1. **缺经济学层**：没有任何工具输出投入成本、预期产量价值、ROI、回本周期——这是农户决策的第一性问题。
2. **缺实时天气**：只有气候基线，没有"未来 7 天"预报，配方无法与真实天气联动。
3. **缺采后/储运**：从种到收就断了，没有采收后处理、储藏条件、损耗率。
4. **作物深度不足**：23 工具里 crop 类只有 1 个，pest 只有 1 个；主粮（水稻/小麦/玉米）无完整生命周期配方。
5. **无畜牧/水产**：纯种植，生态位不完整（但可作为边界诚实声明，不必强补）。
6. **国际化缺失**：全中文，无 i18n，与"A2A 全球 Agent 生态"定位冲突。

**提升到 8.5 的路径**：补经济学 + 实时天气 + 采后三块（见 §4 阶段二），作物深度靠"主粮 5 作物完整生命周期"补足。

---

### 2.2 实用性 —— 6.5 / 10

**优势（实测）**
- 配方有**可直接执行的设定点**：如仙人掌配方 `temperature.day_c=40 / night_c=5`、`humidity 50-80%`、`water_ml_day=10`、`pH=6.5`、`vpd nominal=0.954 kPa`（envelope 0.174–3.688）
- 含 `exception_handling`、`outcome`、`image_consent`、`companion_plants`、`sowing_depth_cm` —— 这些字段说明设计者想过"真实种植会发生什么"
- 每份配方带 `sources[]`，有 `data_quality`、`trial_location`、`source_license`

**缺口（这是"能不能真用"的命门）**
1. **`sources[].url` 大量为空字符串**——用户无法核验来源，等于"引用了但不可查"。
2. **`license=CC BY-NC-SA 3.0 IGO`（非商用）**——与商业化/企业使用直接冲突；`license=unknown` 仍未清零。
3. **`data_quality=modeled`（模型模拟，非田间试验）**——配方是"推算值"不是"验证值"，专业用户一看即知。
4. **无成本/收益**：用户拿到温湿度设定点，却不知道"这套方案投入多少、能赚多少"。
5. **WOFOST 仅覆盖 7 作物**：其余 145 份配方的物候参数是启发式，精度不可承诺。
6. **无本地化适配**：没有"附近农资店/品种/设备"的落地链接。

**提升到 8.5 的路径**：先解决"可信"（URL + license + 明确标注 modeled），再解决"可算账"（经济学层），最后解决"可落地"（本地化）。

---

### 2.3 使用性 —— 5.5 / 10（最大短板之一）

**优势（实测）**
- README 507 行，含 Docker、`mcp.json`、环境变量说明
- 23 个工具全部有 `inputSchema`
- demo 页有 96 个表单控件，功能入口密集

**缺口**
1. **没有快速上手指南**：`docs/` 58 篇文档里**没有一篇 tutorial / quickstart / getting-started**。
2. **工具描述过简**：平均 25 字符，多为"纬度/经度"这类参数级描述；LLM 难以判断"何时该调用这个工具"。
3. **18/23 工具无参数/返回/示例说明**（前序 GAP 审计已确认）——外部开发者接入靠猜。
4. **无示例代码库**：没有 `examples/` 可运行脚本。
5. **错误信息不面向用户**：契约异常是给开发者的，不是给使用者的。
6. **纯中文**：海外 Agent 无法直接消费。

**提升到 8.5 的路径**（成本最低、收益最快）：一篇 15 分钟 QUICKSTART + 23 个工具的三段式描述（何时用/输入/返回示例）+ 5 个可运行示例。

---

### 2.4 互动性 —— 5.0 / 10（最大短板之二）

**优势（实测）**
- 23 个 REST 端点覆盖推荐、诊断、营养、季节、土壤、搜索、BP 筛选、反馈
- 1890 行单页、96 个表单控件、22 个事件监听
- 有反馈闭环端点 `/api/feedback`

**缺口（结构性）**
1. **无流式**：全仓 0 处 SSE / WebSocket / `stream`——所有回答都是"提交后等完整结果"，长任务体验差。
2. **无图表**：0 canvas / 0 Chart / 0 echarts / 0 d3，仅 1 个 SVG——VPD 包络、物候甘特、分区热力这些天然适合可视化的数据全是文字。
3. **无多轮对话**：表单式一问一答，没有上下文记忆的连续追问。
4. **无图片上传 UI**：`type="file"` 仅 1 处且无 `accept="image"`、无 `getUserMedia`——明明后端有 `vision.py`，前端却没入口。
5. **无实时看板/告警**：没有"当前温湿度偏离配方 → 高亮告警"的界面。
6. **无语音/移动端适配证据**。

**提升到 8.0 的路径**：SSE 流式 + 3 个核心图表 + 图片上传接 vision + 多轮会话记忆。这是"从演示页到产品"的关键一跃。

---

### 2.5 前沿性 —— 7.0 / 10

**已具备的前沿要素（实测）**
- **MCP**：23 工具、`tools/list`、inputSchema —— 2024-11 由 Anthropic 提出，2026 已成事实标准
- **A2A**：Agent Card v1.0、23 skills、JWS 签名 —— 2025-04 Google 提出，与 MCP 构成"双协议时代"
- **保形预测**（conformal）：覆盖率保证，`conformal.py` / `conditional_conformal.py`
- **可微分数字孪生**：`agriworld_lite.py` + `agriworld_gradients.py`
- **反事实/因果**：`counterfactual_api.py` / `causal_attribution.py`
- **贝叶斯/联邦校准**：`bayes_calibration.py` / `federated_calibration.py`
- **多模态视觉**：`agent/vision.py`（OpenAI 兼容，可降级）
- **RSI/进化**：`rsi.py` / `evolution.py` / `harness_tree.py`

**前沿缺口**
1. **无实时数据流**（0 MQTT）：数字孪生拿不到"活的"传感器数据，只能是"快照孪生"。
2. **无边缘部署**（0 固件）：算法全在服务端，田间断网即失效。
3. **无向量检索/RAG**（0 embedding）：`local_search.py` 是关键词/规则检索，无法语义召回最新文献与配方。
4. **联邦校准是本地模拟**：不是真正的跨机构联邦学习。
5. **具身闭环未打通**：`control_agent.py` 存在，但 `execution_log` 88 条全 shadow，从未真实驱动过执行器。
6. **无实时天气 API**：预测层与真实气象脱节。

**提升到 9.0 的路径**：实时（MQTT/HTTP）→ 边缘（ESP32 固件）→ RAG（向量检索）→ 具身（真实执行闭环）。这四项正好对应 2026 年"具身智能是农业最难赛道"的行业判断。

## 3. 技术趋势与市场需求（2026）

### 3.1 市场：高增长 + 高门槛
- 全球 AI 农业市场 2024 约 **47 亿美元**，预计 2034 达 **466 亿美元**，CAGR **>26%**。
- 中国精准农业 AI 市场 2025 约 **63.43 亿元**，全球 **181.76 亿元**，2032 全球预计 **1079.62 亿元**。
- 欧盟 2026 启动 **EDIC for Agri-Food**（2026-2028 首期 1500 万欧元），数字农业基础设施成为国家层战略。
- 荷兰瓦赫宁根 **AGROS II** 在温室黄瓜做自主种植——说明"自主决策 + 闭环控制"是前沿主战场。

**对项目的含义**：市场足够大，但赢家不是"功能最多的"，而是"最可信 + 最易用 + 能闭环"的。项目当前"可信度"（URL/license/field data）和"易用性"（无 quickstart）恰好是市场最看重的两项。

### 3.2 技术：MCP + A2A 双协议时代
- 2026 年已成共识：**MCP = Agent 接世界的 USB-C，A2A = Agent 之间的 TCP/IP**。
- 协议层稳定后，竞争转向"**谁的 Agent 能真正完成任务**"——即工具质量、数据可信、闭环能力。
- 农业是"具身智能最难赛道"之一：非结构化环境、长周期、高失败成本。

**对项目的含义**：项目押注 MCP+A2A 是正确的，但"协议正确"只是入场券。真正的壁垒在**数据可信度 + 闭环验证**，这正好是当前最弱的两处。

### 3.3 需求侧：三类用户的真实痛点
| 用户 | 真实痛点 | 项目当前满足度 |
|---|---|---|
| 家庭种植/阳台农业 | "我该种什么、怎么浇水、叶子黄了怎么办" | 中（有推荐/诊断，但无图片入口、无连续追问） |
| 中小农场/温室 | "这套方案投入多少、能赚多少、天气变了怎么办" | 低（无经济学、无实时天气） |
| 农业 Agent 开发者 | "接进来要多久、文档在哪、出错怎么办" | 低（无 quickstart、工具描述过简） |

## 6. 风险与诚实边界

| 风险 | 说明 | 对策 |
|---|---|---|
| 补 URL 时编造链接 | 学术/法务双重风险 | 只填可 200 访问的真实链接；无法核验的标 `url_unverified=true`，不猜 |
| 许可清理误判 | NC 许可不能简单改 | 保留原许可，另加 `commercial_use` 显式字段，由法务确认 |
| 经济学参数失真 | 成本随地区/年份波动大 | 输出区间 + 数据年份 + 地区，不做单点承诺 |
| 实时天气依赖第三方 | Open-Meteo 限流/变更 | 加缓存 + 降级到气候基线 |
| 边缘固件无硬件验证 | agent 无法实测 | 明确标注"设计验证，非田间验证"，待真实节点 |
| 视觉诊断误诊 | 农业误诊代价高 | 必须输出置信度 + 拒识 + "建议人工复核" |

**三条必须写进对外文档的边界**：
1. 配方 `data_quality=modeled` 为模型推算，非田间试验验证。
2. WOFOST 权威参数仅覆盖 7 作物，其余为启发式。
3. `execution_log` 当前全部为 shadow（仿真），无真实硬件闭环。
